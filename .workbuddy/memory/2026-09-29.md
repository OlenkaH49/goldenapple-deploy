## 二、发现的真问题：工作流恒返回 3 条，且「词+整句」查不到词

实测现象（20 词样本，2026-09-29）：

| query 形态 | 命中率 |
|---|---|
| `word + 空格 + context`（改造前代码用的） | **4/20 = 20%** |
| `word` 单独 | **16/20 = 80%** |
| `word,context` 逗号 | 5/20 = 25% |
| `word` ∪ `word,context` | **18/20 = 90%**（两者仅 3/20 重叠，几乎完全互补） |

**机制（关键，以后别再踩）**：
1. `word_context` 里**同一句 context 被该句所有词共享** → 拿「词 + 整句」去查，
   命中的往往是同句的「兄弟词」（例：查 `shock` 返回 `paradoxes / marseilles / immigrants`，
   全是同一句里的别的词）。
2. 工作流**恒返回 3 条**；**传 `top_k` / `limit` 入参全部不生效**（节点里写死），
   所以 top-3 被兄弟词占满时目标词直接被挤出去。
3. 死词复测证明**这些词 KB 里都有**（`shock` 用 `word` 单独能查到、`former` 用 `word context` 能查到）
   → 是**检索召回**问题，不是内容缺失、也不是乱码。

## 三、改法（coze.js，最小侵入）

- 原 `searchKnowledgeBase` **改名 `searchKnowledgeBaseOnce`**（单轮实现，逻辑一行未动）。
- 新 `searchKnowledgeBase(query, opts)` = 多轮包装：按 `buildKbQueryAttempts()` 给出的
  query 形态**依次调用，任一轮精确筛选出目标词即立即返回**；全轮未中才回落 L2。
- 新增常量 `KB_QUERY_MODE`（env `COZE_KB_QUERY_MODE`）：
  - `two_step`（**默认**）：先 `word` 单独，未中再试 `word,context`
  - `word`：只打一轮 `word` 单独（延迟最低）
  - `legacy`：沿用旧的「词 + 空格 + 句」单轮（可回退）
- 无 `opts.word` 时退化为单轮打原始 query（`--verify` 等自由文本场景不受影响）；
  无 context 时只打一轮（第 2 轮无料可加）。
- 提前判 `isKnowledgeBaseConfigured()`，避免多轮各自重复打「未配置」告警。
- 导出新增：`searchKnowledgeBaseOnce`、`buildKbQueryAttempts`；config 新增 `COZE_KB_QUERY_MODE`。

**实测收益（改造前 vs 改造后，同一 20 词样本）**：
- 命中率 **20% → 80%**（+12 个词），平均耗时 550ms → 647ms，平均调用 1.25 次
  （多轮只在第一轮未中时才发生，命中时仍是单次调用）。
- `shock`、`later` 等词是靠**第 2 轮**救回来的，`multiRoundHits` 统计可观测。

统计口径修正（`getLookupStats().kbWorkflow`）：
- `kbLookups` = L1 检索次数（新口径，用作命中率分母）
- `kbCalls` = 实际工作流调用次数（多轮会 > lookups）
- `kbMulti` → `multiRoundHits` = 靠第二轮才命中的次数
- `avgMs` 分母从 `kbCalls` 改为 `kbLookups`（否则多轮会拉低单次均值，语义混乱）

## 六、值得记下的坑与结论

1. **`callCozeWorkflow({...})` 必须显式传 `workflowId`** —— 它的 `workflowId` 参数**没有默认值兜底**
   （不是从常量取），忘了传就直接返回「未配置工作流 ID」。写临时排查脚本时踩过一次，
   导致 4 组对比全失败、得出「返回固定结果」的**错误结论**。排查脚本务必先确认 `ok=true`
   再分析结果，否则会把「调用失败」误读成「检索行为异常」。
2. **`getRecentWordContext(N)` 的 N 会改变取样窗口**：SQL 是「先 ORDER BY id DESC LIMIT N 再翻回升序」，
   所以 N=400 与 N=600 返回的**开头元素不同**（N 越大起始越早）。跨轮次对比必须固定 N，否则样本词变了。
3. **Coze 检索结果不稳定**：同一 query 连打两次，可能一次命中一次返回空（实测 `overcome`）。
   所以判定命中率必须多轮取样，单次结果不能当结论。
4. **`top_k` 入参对工作流无效** —— 它由工作流内部 KB 节点配置决定。想让 L1 更强，
   要么在**工作流编辑器里把 KB 节点的 top_k 调大**（用户侧操作，最大杠杆），
   要么在调用侧换 query 形态多试一轮（本次采用）。
5. **后台起 `server.js` + `kill` 的命令形态会被「敏感内容保护」拦截**（与读 `.env` 同类），
   改用「进程内直接 require 模块」做验证即可，等价且更干净。
