# 2026-10-05 — 「词典式」查词体验（ECDICT 词典层 + 全本地即时出卡）

## 起因
用户原话：「word_context 只有文章里出现过的语境的释义，没有所有释义……现在的查词实在太慢了」。
要的是：点词 → **语境释义（本句里的意思）+ 完整释义（词典全部义项）** 两栏；
先出可行性 + 提速评估，再动手。

三项决策（AskUserQuestion，全选推荐项）：
1. 词典口径 = 纯字母 ≥2 字符 + 有中文释义 → 365,058 条 / 约 58MB
2. AI 策略 = **不再每次自动调 AI**，改成卡片里按钮触发
3. 预取 = 进阅读页时批量预取本文所有词的词典释义

---

## 结论：慢的根因不是索引，是「每次点词都要往 LLM 跑一趟」
- 词典单次点查 **21µs**（20,000 次共 422ms）；单次 HTTP 端到端 **0~2ms**
- 原来冷词要 8.5s（LLM 往返 4~13s）→ **约 2800 倍**差距
- 顺带发现两个更严重的问题：
  - ① L1 网络调用**排在本地层之前**，每个冷词白等 0.3~1.2s（L1 一轮 604ms、two_step 两轮 1011ms）
  - ② L1 知识库**陈旧且命中率极低**：本地 L2 命中 12/12，L1 只中 3/12

## ECDICT 导入（`import_ecdict.js`，新建）
- 下载通道：`raw.githubusercontent.com` 直连 66MB 超时；jsDelivr 20MB 硬上限 403；
  `ecdict.mini.csv` 只有 4KB 空壳；`media.githubusercontent.com` 404 →
  **唯一可用 `gh-proxy.com`，实测 10 MB/s（6.5s 下完 62.9MB）**
- 过滤口径踩坑：`had / been / went / swung / began` 在 ECDICT 里**没有考试标签、bnc/frq 全 0**
  （靠 `exchange` 的 `0:have` 反指原形）。按「常考词」筛 → 文章覆盖率只有 86.8%；
  改成「纯字母 ≥2 + 有中文释义」→ **97.4%**
- CSV 解析**必须带引号状态机**（`translation`/`definition` 含内嵌换行，`split(',')` 会切错）
- **ECDICT 义项分隔符是字面量 `\n`（hex `5c 6e`，反斜杠+n 两个字符）**，不是真换行 →
  必须 `split(/\\n|\r?\n/)`；`better` 曾显示成一整条 `a. 较好的\nadv. 比较好`
- 音标转写：`'`→`ˈ`、`,`→`ˌ`、`ә`(U+04D9 西里尔)→`ə`、`:`→`ː`。数据是**英式音标**（`ˈbetə` 不是 `ˈbetər`）
- 导入耗时 **4.8~4.9 秒**（74,578 条/秒）：导入期 `journal_mode=OFF` + `synchronous=OFF`，
  5000/批事务，完事 `VACUUM` + `ANALYZE` + `wal_checkpoint(TRUNCATE)`，最后原子 `renameSync` 替换
- **独立词典库文件 `data/dictionary.db`**，运行期 `readonly: true`，与 `app.db`（用户数据）物理分离：
  词典是可整体替换的只读参考数据集，各自加锁不抢写锁

## 兜底链（`db.js getDictionaryEntry`）
**ECDICT 里 0 条含撇号的词条**（`LIKE '%''%'` = 查不到任何行）→
`don't / isn't / o'clock / what's` 这些初中最高频词本来全都「未收录」。兜底顺序：
1. 原词直查
2. 弯引号归一化（正文常是 `’` U+2019，词典只有 `'` U+0027）
3. **缩写表** `CONTRACTIONS`（约 35 条）→ 展开式 + 取实词词条（`don't` → `＝ do not` + `do` 的释义）
4. 所有格剥离 `'s` / `'s` / `s'`（`student's` → `student`）
5. 去掉全部撇号（`rock'n'roll`）
6. 连字符取首段（`well-known` → `well`）
返回值多挂 `query` / `via`（兜底方式）/ `contraction`（展开式）；前端挂小徽章说明「所有格 → student」。
兜底后 2000 次查询 79ms（39µs/次，直查 21µs）。

## 三层查询顺序调整（`coze.js lookupWordWithLayers`）
原来是 `L1 知识库(联网) → L2 语境库(本地) → L3 AI`。
改成 **词典层（同步）→ L2 语境库（本地）→ 联网层**，并**默认关闭联网**：
```js
const enableRemote = opts.enableRemote === true || opts.enableAI === true;
```
- L1 条件：`if (!contextDefinition && enableRemote && isKnowledgeBaseConfigured())`
- L3 条件：`if (!contextDefinition && enableRemote)`
- 主释义兜底：`definition = contextDefinition || dictFirstLine || null`
- 返回新增 `contextDefinition` / `contextSource` / `dictionary` / `dictElapsedMs`
- `lookupStats` 新增 `dictHits` / `dictMisses` / `dictionaryLayer` / `kbDisabled`
- 命中层级 `layer` 新增 `dictionary`；**L1 知识库命中刻意返回 `source: 'context'`**
  （前端 `sourceLabels` 只认 context/ai/none）

## 前端词卡（`app.js`）
- `dictionaryCache` + `prefetchDictionaryForArticle()`：进阅读页一次性批量预取。
  词表 = **「AI 词表」∪「正文正则抽词」** —— 只取 AI 词表的话，正文里点得动但不在词表里的词
  点下去要先等一次 HTTP（实测 article_001 只预取到 20 个）→ 合并后点得动的每个词都在本地
- `openWordCard()`：**同步出卡**（词典 + 文章释义占位）→ 后台打一次只查本地的接口（~1ms）核对精确本句释义
- 卡片结构：`wordRow` + `phoneticHtml` + `badgesHtml` + `contextHtml` + `dictionaryHtml` + `addMeaningHtml` + `sentenceHtml` + `sentenceTransHtml`
  （删掉了旧的 `contentHtml` / `sourceHtml` / `pendingHtml`）
- 「联网深查」按钮出现规则：来源是 **文章释义 / 通用释义 / 什么都没有** 时给；
  已是 **本句释义 / 知识库 / AI 生成** 就不给（已钉进测试）
- **问题3 的 3 秒逻辑换了判据**：从旧的 `pending && definitions.length===0` 改成
  「词典义项 + 语境释义**都为空**」：
  - 已有任意释义 → 不放「本句翻译」按钮
  - 都空但后台还在查（`contextPending` / `dictionaryPrefetchPending`）→ 数 3 秒
  - 都空且**已确定查不到** → 立刻放按钮（不等 3 秒）
  - 为此 `updateWordCardIfOpen` 取消了「无新信息就早退」，改成始终重绘 → `contextPending` 落下后自然立刻放按钮
- `updateWordCardIfOpen` 用 `data-ctx-def` / `data-ctx-src` 兜住「越刷新越少」
- CSS：`.word-card` 加 `max-height:72vh; overflow-y:auto`（长词义项十几条会顶出屏幕）

### 写测试踩的坑
- **打桩 DOM 的 `querySelector` 会「永远返回元素」** → 坏 HTML（标签没闭合 / class 拼错）也会判通过。
  已把打桩升级为**真的按 innerHTML 解析 class**，没有该 class 就返回 `null`（与真实 DOM 一致）
- 截图里卡片半透明一度以为是 bug，实测是 `animation: fadeIn 0.2s` 未跑完
  （t≈100ms 时 `opacity` 0.64）→ 测试里加 `waitForFunction(opacity==='1')` 再截图
- 浏览器测试的两个断言一开始写反了：
  ① 以为「有语境释义就不给联网深查」→ 实际规则是按**来源**（文章/通用释义才给）
  ② 以为「刚出卡时本句翻译按钮必隐藏」→ 本地接口 2ms 就回来，按钮会**立刻**放出，断言与产品行为冲突
- 真实浏览器自动化环境（2026-09-30 已打通）：`playwright-core` + `chromium.launch({channel:'msedge'})`，
  跑脚本要 `NODE_PATH=<managed workspace>/node_modules`

### 经验
- 同一个延迟数字（3000ms）现在只剩**一处**在用：`SENTENCE_HOVER_DELAY_MS`（悬停浮层）。
  以后看到「3 秒」相关的日志/注释，先分清是哪一条路径。
