## 第二轮修复：点击卡顿 + 句子译文不渲染（2026-09-28 晚）

用户报了 2 个线上问题，逐条定位后修改：

### 问题一：点词卡顿

**根因（两部分）**
1. **回写是同步阻塞**。`lookupWordWithLayers` 第三层里 `dbOps.saveWordContext()` / `dbOps.addWordDefinition()`
   是 better-sqlite3 的**同步** API，直接写在请求链路里。若另一进程（同步脚本）正持写锁，这里要干等到
   `busy_timeout`（5s）超时才返回，用户点击就卡住。
2. **L2 语境库检索没走到理想索引**。`getWordContext` 是 `WHERE word = ? AND context = ? ORDER BY id DESC LIMIT 1`，
   原来只有 `idx_word_context_word(word)` 单列索引 → 先用 word 捞回该词**全部**语境再逐行比 context。
   高频词可能有几十上百条语境，等于每次点击白扫上百行。

**改法**
- `db.js`：新增复合索引 `idx_word_context_word_context ON word_context(word, context)`（放在 `initDB` 的建表块里，
  `IF NOT EXISTS` 对存量库自动补建，无需单独迁移函数）。
  实测：热词 "translation"（8 条语境）× 20000 次，走索引 118ms ｜ 强制全表扫 411ms → **约 3.5×**。
  `EXPLAIN QUERY PLAN` 确认 `SEARCH word_context USING INDEX idx_word_context_word_context (word=? AND context=?)`，
  且 `ORDER BY id DESC LIMIT 1` **不需要**额外 TEMP B-TREE（id 即 rowid，索引内天然有序）。
- `coze.js`：新增并导出 `scheduleWriteBack(label, fn)` —— `setImmediate` + `try/catch` 包住回写。
  第三层把两条写库操作整体搬进 `scheduleWriteBack`，并把 `definition`/`part_of_speech` **快照成局部常量**
  （`aiDefinition` / `aiPos`），避免后续兼容层改写 `definition` 时污染这次回写。
  实测：`lookupWordWithLayers` resolve 时写库次数为 0，`setImmediate` 后共 2 次；响应返回→首次回写间隔 **0.25ms**。

### 问题二：句子翻译成功但网页不显示

**根因**：`app.js` 的 `pollArticleProgress` **压根没读 `status.sentencesReady`**。
后端 `queue.js` 早就把句子翻译单独落盘到 `taskMap.sentences` + `sentencesReady=true`（三个工作流并行、
谁先完成谁先就绪），但前端只在 `status.wordsReady` 为真时才调 `applyPartialProgress`。
→ 句子先翻译完、单词释义还在跑时，译文永远不渲染；`buildSentenceList()` 返回空，
正文里也就没有 `.article-sentence` 元素，句子悬停浮层自然不工作。

**改法**
- `applyPartialProgress` 拆成 words / sentences / questions **三条独立合并逻辑**：
  - 只处理传进来的那一项，`null`/未就绪的项**原样保留**，不再用空值覆盖；
  - 记住 `prevCount` / `prevLen`，**内容真的变了才 `renderArticleWithTranslations()`**。
- `pollArticleProgress` processing 分支改为 `if (status.wordsReady || status.sentencesReady)`，
  各自按 ready 标记传值（未就绪传 `null`）；`completed` / `failed` 分支补上 `sentencesReady: true`。
- `openAnalyzedArticle` 初始化 `sentencesReady`；上传入口传 `sentencesReady: false`。

**顺手修掉的第二个反向 bug**：原代码在 `wordsReady` 分支里写 `currentArticle.sentences = part.sentences || []`。
即「单词后到」会把已经渲染好的句子**冲成空数组**。
**顺手修掉的第三个体验问题**：原代码只要 `wordsReady` 为真就无条件重绘正文，
而 `renderArticleWithTranslations` 是重建 `readContent.innerHTML` → **每 2 秒轮询都白重绘一次**，
用户正在划的选区、悬停浮层被反复清掉，观感就是「卡」。现在改为有变化才重绘。

**`sentenceList` 结构核对结果：一致，无需改**
- 真实任务（`processSentenceBatches`）产出 `{sentence, translation}`
- mock（`generateMockSentenceList`）产出 `{original, translation}`
- 前端 `buildSentenceList`（app.js 约 3167 行）的兼容表 `s.original || s.en || s.sentence || s.text || s.english || s.content`
  两者都能取到。所以问题只在轮询分支，不在数据格式。

### 实现细节备忘
- 工作流响应的 `data` 是 **JSON 序列化字符串**（`"{\"word\":...}"`），必须二次 `JSON.parse`；
  官方文档明确「部分场景下可能返回非 JSON 结构的字符串」→ 解析失败时保留 `dataRaw`，不要把原文当命中。
- 输出形态做了三层兼容：
  ① `{word,context,definition}` 直接吃；② `{output:"<JSON 字符串>"}` / `outputList[].output` 走 `pickExactWordRecord`；
  ③ 纯文本 CSV 行（`"word","context","definition"`）走新增的 `deriveKbSlicesFromText()` 兜底 → `parseDefinitionFromSlice` 逐行严格匹配。
  三种都要过「word 完全匹配」这一关，避免返回别的词的释义。
- `callCozeKnowledgeApi()` 的守卫从 `isKnowledgeBaseConfigured()` 改成只校验「令牌 + BASE_URL」——
  因为前者语义已变成「L1 工作流就绪」，而该函数是直连知识库 OpenAPI（现在只剩 `listKnowledgeDocuments` 诊断在用）。
- 重试语义：4xx / 业务错误码不重试；429 / 5xx / 网络超时重试（退避 1s→2s→4s）。
  node-fetch v2 的 `timeout` 生效（实测 1.5s 超时 + 1s 退避 + 1.5s 超时 = 4038ms，共 2 次请求）。
- `/v1/workflow/run` 官方限制：**非流式接口 90 秒内无响应会被网关断开**；工作流必须**已发布**；
  含数据库节点/变量节点的工作流**必须**带 `bot_id`（已留 `COZE_KB_WORKFLOW_BOT_ID` 开关）。
