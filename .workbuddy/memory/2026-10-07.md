## partial 文章「兜底 UI + 只重跑句子翻译」（09:50 起）

用户需求原文：
> 文章状态是 partial 时，前端：文章正文正常显示 / 单词释义正常显示 / 题目正常显示 /
> 句子翻译区域显示「⚠️ 句子翻译暂时不可用 [重试]」。
> 用户点「重试」：调 /api/retry-sentences/:articleId，只重跑「句子翻译」任务；
> 成功 → 更新状态为 completed；失败 → 保持 partial。
> 要求：修改 app.js、server.js、queue.js，加日志，直接改代码。

### 实现

**db.js**（比用户点名要多改一个文件）
- 新增 `updateArticleSentences(id, sentences, {status, sentencesError})`。
- ⚠️ 关键理由：**不能复用 `updateArticleQuestions`** —— 后者 `SET questions = ?`，
  重试译文时题目没变，传 undefined 会把已经生成好的题目清成 **NULL**，
  用户点一次「重试」反而把题目弄丢。新函数只碰 `sentences / status / sentences_error / updated_at`。
  这条是本功能最容易踩的坑，测试里用 `questions === QA_Q` 专门守（A5/A7/B6/C4/G7/G16）。

**queue.js**
- 新增 `runSentenceRetry(articleId)` / `startSentenceRetry(articleId)` / `retrySentences(articleId)` / `isRetryingSentences(articleId)`。
- 只调 `coze.analyzeSentencesWithCoze`，**不跑 word / quiz**：省额度（用户明确不充值）+ 不用可能更差的新结果覆盖已有好结果。
- **重试期间 DB 的 status 一直保持 partial 不变**，只有拿到最终结果才一次性翻 `completed` 或写回新原因。
  好处：进程中途崩掉文章仍是 partial（可再点重试），不会卡死在 processing。
- `sentences.length === 0` **也算失败**（否则又是一次静默降级：status 说成功、界面没译文）。
- 失败时用 `prevSentences`（而不是硬写 `[]`）落库，避免误删已有数据。
- 并发幂等靠 `sentenceRetryMap`（articleId → promise），同篇并发只打一次 Coze。
- `startSentenceRetry` 还会检查 `taskMap`：整篇分析还在跑时拒绝并发重试。

**server.js**
- 新增 `POST /api/retry-sentences/:id`。契约：**立即 202**，后台异步跑，前端轮询。
  没做成同步等结果是因为句子工作流单次可能几十秒（长文 timeout 更久），挂着几十秒的 HTTP 容易
  被中间层掐断、用户也只看到按钮转圈。
- 分支：404 文章不存在 / 200 `alreadyDone`（已是 completed 且有译文 → **不调 Coze**）/ 409（pending、processing）/ 202 正常。
- `/api/article-status/:id` 的 partial 分支透出 `sentencesRetrying`（= `queue.isRetryingSentences`），
  completed 分支补 `sentencesRetrying: false` 让前端可无条件读。

**app.js**（兜底 UI 主体）
- `showSentenceFailedNotice` 文案改为「句子翻译暂时不可用」，失败原因挪进 `title`（对用户无意义、留着排查）。
- 新增 `setSentenceRetryButtonState('idle'|'busy')`、`retrySentenceTranslation()`、`pollSentenceRetry()`、`applyRetriedSentences()`。
- 按钮忙闲状态绑 `sentenceRetryTargetId`（而不是一个全局布尔）→ 用户重试途中切到别的 partial 文章时，
  新文章的按钮不会被误置成「重试中…」。

### 问题一：句子翻译成功（17 句）但浮层显示「暂无翻译」

**根因是两件事叠加**（不是单点 bug）——只修任何一件都还会复现：

**① 文章列表刷新把「已加载好的详情」冲成空壳（主因）**
`loadArticlesPage` 里首页重载是 `ARTICLES.length = 0` 后整表重建，再用
`ARTICLES[i] = Object.assign({}, ARTICLES[i], a)` 合并 —— 而 `a`（`mapServerArticle` 产物）
是**轻量版**：`sentences: []` / `words: {}` / `questions: []` / `detailLoaded: false`。
于是任何一次列表刷新（首页重载 / 加载更多 / 下拉重试）都会把已经拉到手的译文**原地清空**。
而列表末尾的补拉守卫是 `!cur.detailLoaded && !articleDetailAsked[cur.id]` ——
用户此前点开过这篇时 `articleDetailAsked[id]` 已经是 `true`，**永不补拉**。
结果：后端日志「✅ 句子翻译成功（17 句）」，前端 `currentArticle.sentences` 恒为 `[]`，
`buildSentenceList()` 走本地切句兜底（译文全空）→ 悬停浮层「（暂无翻译）」。

修复：
- 新增 `mergeServerListItem(existing, item)`：详情已加载的文章，轻量字段（标题/正文/状态/时间）
  照常更新，**重字段（sentences/words/questions/detailLoaded/三个 ready 标记）原样保留**。
  首页重载改为「先留快照 → 清表 → 按快照 merge」，不再一刀切清空。
- 补拉闸门从「一次性 `articleDetailAsked`」改成 `shouldFetchArticleDetail()`：
  已加载→不拉；正在拉→不拉；**失败 5 秒退避期内→不拉**（新增 `articleDetailFailedAt`）。
- `loadArticleDetail` **失败时 `delete articleDetailAsked[id]`** —— 旧实现一次瞬时失败就把这篇
  永久钉死在空壳状态（这是 ① 的放大器）。
- `renderArticle` 末尾加**自愈**：`!detailLoaded && shouldFetch` → 自动补拉 + 重渲染。
  无论用户从哪条路进阅读页（列表点开 / 首页刚回来 / 轮询落库）都能救回来。
- `mapServerArticle` 透出 `serverHasSentences`（列表接口本来就有 `hasSentences` 字段），
  用来区分「本来没译文」和「有译文但没加载到」。

**② 正文掉空格导致句子匹配不上（次因，但同样要修）**
那篇文章的正文是 PDF 抽的：`With the rapiddevelopment of ... ofordinary people`，
而后端 sentenceList 里空格是正常的 → **17 句里 11 句逐字不相等**，只能靠「顺序兜底」对齐。
兜底恰好对得上纯属运气：实测 `upload_1790413176880` 是 33 句 vs 39 片段、
`upload_1790329600818` 是 58 句 vs 21 片段，片段与句子数一变就错位。

`sentenceMatches` 增加「压扁后相等 / 压扁后包含 / 压扁后前 30 字母相等」三级判定。
实测该文 **6/17 → 17/17** 靠文本匹配命中，不再依赖顺序兜底。

### 问题二：粘贴导致词粘连（rapiddevelopment = rapid + development）

选型：**用本地 ECDICT 当词表做动态规划分词**，而不是引第三方分词库、也不用 AI。
理由：零新依赖、零联网、零 Coze 额度（符合「不充值」决策），且 1~20ms 出结果。

- `coze.segmentGluedWord(word)`：① 先查合并词（收录就直接返回，不拆）；
  ② 收集该词所有长度 ≥2 的子串，**一次 SQL 批量查词典**；③ DP 取 `Σ(词长²)` 最大的
  「每段都在词典里」的切分；④ 无合法切分 → 不拆（宁可不说，绝不乱拆）。
- **踩到的坑（值得记）**：ECDICT 的 `bnc` / `frq` 是**排名**（1 = 最常用），不是次数。
  第一版直接拿它当词频做 tie-break，于是**反过来奖励生僻词**：`themore` 被拆成 `them + ore`
  （them 的 BNC 排名 46212、ore 8191；而 the 是 1、more 是 74）。改成 `Σ 1/排名` 后正确。
- 质量护栏：`isTrustedGluePart` —— 段长 ≥4 直接可信；短段必须有词频/柯林斯/牛津信号，
  否则 ECDICT 里的 `bc`/`aa` 这类噪声会把 `rapiddevelopment` 拆成 `ra + pid + development`。
  另加输入上限 30 字母（`aaaaaaaa…` 60 个 a 曾被拆成 12 个 `aaaaa`）。
- AI 兜底 `splitGluedWordWithAI`（专名粘连拆不出时用），**默认不启用**：
  只有前端「🔎 用 AI 拆开这个词」按钮才会带 `?ai=1`。AI 返回后**每段仍回查词典**，
  且要求拼回去等于原串 —— AI 只负责切位置，不负责编词。
- `GET /api/glue-word/:word`：合并词 + 分开段各自的义项；`?ai=1` 才允许 AI。
- 前端：`openWordCard` 在「词典 + 语境 + 通用词库全都没有释义」时触发拆词；
  卡片新增「拆分释义」区块，按用户要求排成「合并 → 分开 → 分开」三行，各带音标 + 最多 4 个义项；
  结果只重绘「用户仍在看的同一张卡」（`currentWordCardKey` 比对）；
  收藏释义也兜一层「rapid：迅速的；development：发展」，不让粘连词收藏成空。

## 五、「释义锁」（猜词模式）（11:45 起）

用户需求核心理念：**先猜 → 对照 → 自行判断**，不强制、可跳过。六条要求：
① 全局锁（默认 on，顶部开关，localStorage）；② 点词锁上给猜测框（提交后并排「你的猜测 / 📍正确释义 / 📚其他释义」，**不判对错**）；
③ 句子悬停锁上给「🤔 先猜一猜这句话的意思」+ [🔓 看翻译]；④ 独立记忆 `unlockedWords` / `unlockedSentences`；
⑤ 交互简单不强制；⑥ 状态保存。
**用户明确的一条红线：锁只影响「显示」，不影响「加载」** —— 后端照常调 API、词典/L2/L3 照常加载，解锁那一刻纯本地重绘、0 网络 0 等待。

### 实现（app.js 单文件 + index.html）

**状态层**（`app.js` 约 1543-1756）
- 三个 localStorage 键：`guessMode`('on'|'off') / `unlockedWords` / `unlockedSentences`。
  读写全包 `try/catch`（`guessStorageGet/Set`）—— 无痕模式下 `setItem` 会抛，
  **绝不能因为存不了偏好就让「点词」这个核心功能失效**。
- `unlockedWords` 用**数组而非 Set**：要保插入顺序才能「超上限丢最旧」。
  上限 `GUESS_UNLOCK_MAX = 800`，句子 key 截断 300 字（localStorage 总共 ~5MB，不设限会被长期使用撑爆）。
- `sentenceLockKey()` 复用正文匹配的 `normalizeSentence()` 再截断 —— 同句因重渲染多一个尾空格、
  或标点全角变半角，就不会被当成两句、逼用户重新猜一次。
- 判定函数：`isMeaningRevealed()` / `isSentenceRevealed()`（查看模式下恒 true）。
- **★ 关键实现决定：`loadGuessLockState()` 在脚本载入时直接调用，不放 `DOMContentLoaded`。**
  两个理由：① app.js 在 `</body>` 前加载、此时 localStorage 已可用，「默认锁上」在第一帧渲染前就定死，
  不会先按默认画一遍再跳；② **无头测试不会派发 `DOMContentLoaded`** —— 放进去状态永远载入不了，
  整个功能在测试里静默失效（本轮真踩过）。DOM 相关的 `syncGuessLockButton()` 才留在 DOMContentLoaded。

**词卡三形态**：`__guessView` ∈ `'guess'`(只画猜测框) / `'echo'`(刚提交，多一行「你的猜测」) / `'full'`。
- `__guessView` 是**显式指定**、不是重新判定 —— 因为「提交」那一刻词已写进 `unlockedWords`，
  重新判定会得到 `full`，把用户刚敲下的那句猜测从屏幕上抹掉（他连自己写了什么都看不到）。
- `guessView === 'guess'` 时连**音标 + 徽章一起藏**：徽章里的「原形 student」「牛津3000」「柯林斯 5★」
  基本等于把答案递过去。**动作区（标记/收藏）整块不渲染** —— 否则「先收藏、再去生词本看释义」就是绕过锁的近路。
- 猜测草稿 `guessDraftByKey` / 已提交结果 `guessResultByKey` 放在**模块级字典**而非 `wordData` 里：
  后台核对（~1ms）、拆词结果回来都会重绘卡片，用模块级字典存，任何一条重绘路径都能自然带上。

**★ 本轮修出的真 bug（`showWordCard` 尾部）**：`currentWordCardData` 原来只 `Object.assign({}, wordData, …)`，
而 `wordData.__guessView` 在「刚点开」时是 undefined → `updateWordCardIfOpen` 里的
「猜词形态下只更新内存、不重绘（保住输入焦点）」判断永远为假 → **用户一点开就开始打字，
1ms 后后台核对回来就会重建输入框**。修法：把**已判定**的 `guessView` 显式写回 `currentWordCardData`。

**句子浮层**（`showSentenceHoverPanel` / `onSentenceRevealClick`）
- 锁上时译文位置显示「🤔 先猜一猜这句话的意思」，`.shp-reveal` 去掉 `hidden`。
- 译文**不是没拿到，是拿到了先不显示**（就在 `translation` 参数里）→ 点「看翻译」是纯本地重绘。
- 点「看翻译」时译文按 idx **现取**（`resolveSentenceAt`），并把待解锁原句记在
  `panel.setAttribute('data-lock-sentence')` 上，点击时若 idx 取不到句子还能兜住。
- 锚点要有记忆（`panel._anchorEl`）：用户点浮层按钮时鼠标在浮层上、`sentenceHoverEl` 已被清空，
  没有记忆浮层会当着用户的面跳回视口顶部。

**index.html**：`#guessLockBtn`（`onclick="toggleGuessLock()"`，`.lock-on` 暖色高亮）、
`.shp-reveal` 样式、`#shpRevealBtn`。指纹 `app.js?v=20261007_3` → `20261007_4`。

### 设计取舍（有意为之，别当 bug 改）

- **不判对错**：用户明确要求「自行判断」→ 提交后不加颜色、不打勾叉。测试用 `[✔✘✅❌]` 正则反过来守。
- **锁上是「不画」，不是「不查」**：看到 `if (lock) return;` 提前跳过请求的写法一定是错的。
- **解锁不可逆（本会话内）**：没有「重新上锁」入口 —— 用户要求「不强制、可跳过」，
  加一个反向开关只会让界面变复杂。要重置就让用户清 localStorage。
- 顶部开关切模式时会 `hideSentenceHoverPanel()` + 原地重渲染当前词卡（丢掉 `__guessView` 按新模式重判）：
  浮层内容与模式强相关，留在屏幕上会自相矛盾。
