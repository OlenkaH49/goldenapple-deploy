### 关键结论
- Coze 官方接口：上传 `POST /open_api/knowledge/document/create`（本地文件 base64，仅支持 pdf/txt/doc/docx）；检索 `POST /open_api/knowledge/document/search`（knowledge_id / query / top_k / score_threshold / query_type）。
- **CSV 不在 Coze 支持的文件类型里**，故 CSV 内容以 `file_type: txt` 上传，并用 `chunk_strategy.separator = "\n"` 让「一行一条记录」成为独立切片，检索结果可直接解析。

## 追加：searchKnowledgeBase 增加「精确筛选」（同日晚）

需求：知识库返回的结构里是 `outputList`，每个 `output` 是一段 JSON；检索属于「召回」，一次会带回多个不相关的词，需要只保留 word 与查询词完全匹配的那一条。

### 改动（仅 `coze.js`）
- 新增辅助函数：`normalizeKbWord` / `kbRecordDefinition`(兼容 definition|meaning|def|释义) / `kbRecordPos`(兼容 part_of_speech|partOfSpeech|pos|词性) / `kbRecordContext` / `parseKbOutputRecord`(支持 ```json 围栏、对象、JSON 数组) / `collectKbWordRecords`(深度≤6、对象去重) / `pickExactWordRecord` / `kbRecordToSliceLine`。
- `searchKnowledgeBase(query, opts)` 新增 `opts.word` / `opts.context`；返回体新增 `exact`（精确筛选取用的那一条）与 `hitsAll`（原始召回，便于排查）。**未显式传 word 时退回 query 的第一个词**，保证单独调用也有筛选能力。
- 匹配规则：忽略首尾引号/空白 + 大小写（查询词常是句中大写形式）；同词多条按「语境完全一致 → 前缀一致 → 第一条」择优；有 word 无 definition 视为未命中。
- **JSON 记录模式**（解析出候选记录时）：`hits` 只保留匹配那一条，其余一律丢弃；无匹配则 `hits=[]` 且 `exact=null`，L1 按未命中处理 → 不再返回其他词的释义。
- **切片模式**（无 JSON 记录，即旧的 `items[].slice` CSV）：`hits` 保持原样不动（避免回归），仍由 `parseDefinitionFromSlice` 逐行严格匹配 `fields[0] === word`。
- `lookupWordWithLayers` 第一层优先采用 `kbRes.exact`，匹配方式标记为 `exact-word`；日志新增候选记录数/匹配数/被丢弃的词。

### 验证
- 本地 mock 21/21 通过，含：3 条召回只留 1 条、深层 `data.data.outputList`、```json 围栏、字段名 `meaning`、大小写不敏感、无匹配不返回错释义、`output` 为 JSON 数组、有 word 无 definition、同词多条按语境择优、**切片模式回归不受影响**、L1 端到端命中与回落。

## 追加：sync_to_knowledge.js 重构（攒批上传 + 硬超时 + 自动清理）（同日晚）

需求：完善 `sync_to_knowledge.js`，实现「定时同步 word_context 到 Coze 知识库」。用户给定接口 `POST /v1/datasets/{dataset_id}/documents`，body `{documents:[{content, file_type:"txt"}]}`，要求错误处理 + 超时 + 重试。

### 用户拍板的 4 项策略（第二轮确认）
1. 上传节奏 → **攒批上传 + 自动清理**（不是每 5 分钟传一批新文档）
2. 去重 → **本地标记为主**（不做逐词真实检索）
3. 进程托管 → **独立常驻进程**（`npm run sync:daemon`）
4. CSV 第 4 列 → **加**（`part_of_speech`）

### 前置关键发现：Coze 文件数硬上限 300
官方限制（`docs.coze.cn/guides/knowledge_limits`）：**每个知识库最多 300 个文件**；单个 txt ≤ 5 MB；分段总数上限 10000；单分段 ≤ 5000 字符。→ 「每 5 分钟新建一个文档」= 288 个/天，约 1 天就撞墙。故改为 **扫描 5 分钟一次（本地零成本）+ 攒批上传 + 自动清理**。

### 踩坑记录
1. `ALTER TABLE ADD COLUMN ... DEFAULT (datetime('now'))` → `Cannot add a column with non-constant default`。**better-sqlite3/SQLite 的 ADD COLUMN 只接受常量默认值** → 改为加可空列 + 单独 UPDATE 回填。
2. 双进程并发迁移：`PRAGMA table_info` 先查后改的 check-then-act 竞态 → 第二个 `ALTER` 抛 `duplicate column name` → 每列 `ALTER` 各自 try/catch。
3. **探测自毒（真实 bug，测试中抓到）**：探测词原先写死 `__kb_probe__`，上一轮残留的探测记录会让**失败的上传**被误判为成功 → 改为每轮唯一标记 `` `${KB_PROBE_DOC_PREFIX}w${Date.now()}` ``，正向判定必须来自 `kb.exact` 且 word 相符。
4. 探测失败时白等满 45s → 加反向判定：两次回查都无可解析记录即提前失败。
5. Windows 上 `child_process.spawnSync` 偶发 `EBUSY`（`status: null, error: EBUSY`）→ 测试驱动改用异步 `spawn`。
6. mock 跨场景残留上传记录导致断言错位 → 隔离场景前 `mock.uploads.length = 0`。
7. mock 在解码失败时仍伪造「可匹配」记录，导致把错误编码判成 `text` → 改为解码失败就返回空（贴近真实行为）。
8. 硬超时场景中被延迟/abort 的响应仍在改状态 → 处理函数加 `if (res.destroyed) return;`。
9. 旧代码用 `running` 布尔量防重入：一旦某次 run 卡死，`running` 永远为 `true`，**后续所有 tick 被静默跳过** → 换成 `AbortController` + deadline + epoch + `finally` 复位。
10. `node-cron` 的 `executeTimeout` 只对 background/fork 任务生效，**inline 任务没有超时** → 必须自己实现硬超时。
