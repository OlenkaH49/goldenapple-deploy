### 问题1——句子翻译触发不灵（「必须在句子上移动两下再停下」）
**两个根因（app.js 句子悬停）**：
1. `scheduleSentenceHover` 开头 `if (panel.classList.contains('visible')) return;`
   → 上一句的浮层还没消失时进入下一句，**这一轮永远不排期**，必须等浮层关掉后再动一次鼠标。
2. 每次 `mousemove` 都 `clearTimeout + setTimeout` → 鼠标在句子上**任何轻微抖动都重置 3 秒** → 极难触发。

修复：改用**幂等排期** `armSentenceHover(el)`：
- `sentenceHoverArmedIdx === idx && sentenceHoverTimer` → 直接返回（**同句内不重置计时**）；
- `sentenceHoverVisibleIdx === idx && 浮层 visible` → 返回（同句已展示不必重排）；
- 换句时先 `clearTimeout` + `hideSentenceHoverPanel()`（收掉上一句浮层）再重新排期；
- `onSentenceMouseOver` **进入即排期**（不再依赖后续是否还有 mousemove）；
- 计时到点前校验 `sentenceHoverEl === el` 才弹（快速划过不弹）。
- `onSentenceMouseOut` 不再无条件清 `sentenceHoverEl`：`relatedTarget` 是另一句时只清计时、保留句柄，
  避免「mouseout 先于新句 mouseover、且新句没有 mousemove」时已排期的计时被误判丢弃。
- 延迟抽成常量 `SENTENCE_HOVER_DELAY_MS = 3000`（原来是写死的 3000）。
- `showWordCard` 改用 `clearSentenceHoverTimer()`（原来只清 timer 变量，漏了 armed 索引）。

## 问题2 —— 单词翻译 & 句子翻译「出不来」（真实根因，已浏览器复现）
**① 单词翻译：`handleWordSpanClick` 的硬拦（直接原因）**
旧代码：`if (!currentArticle || currentArticle.wordsReady === false) { toast('释义生成中，请稍候...'); return; }`
而单词释义工作流失败/超时后，`queue.js` 的 catch 分支**不会**置 `wordsReady=true`
→ 前端 `wordsReady` 永远 false → **点词被永久拦掉，只弹一个 toast，卡片永远不出来**。
浏览器实测：`mouse.down/up` 点词无卡片；**直接调 `handleWordSpanClick(span)` 也不出卡**（排除事件问题）。
修复两层：
- **queue.js**：`wordPromise.catch` 里用 `cacheMap`（word_cache 通用释义）兜底并置 `t.wordsReady = true`；
- **app.js**：删掉硬拦，点词统一走 `openWordCard` 的「即时出卡 + 后台精修」契约。
另：`server.js` 的 `failed` 分支补返回 `sentences`。

**② 句子翻译：重绘把已排期的悬停计时作废**
`renderArticleWithTranslations()` 每次重绘都重建 `#readContent` 的 innerHTML，
但**没有清 `sentenceHoverEl`** → 旧节点被销毁后，已排期的 3 秒计时到点时
`!sentenceHoverEl || sentenceHoverEl !== el` 成立 → **直接丢弃不弹**（必须再动一下鼠标）。
修复：重绘后统一 `sentenceHoverEl = null; clearSentenceHoverTimer(); hideSentenceHoverPanel();`
另加渲染日志：`sentenceList=N 句 | 切出片段=M | 匹配成功=K | 生成 .article-sentence 节点=K`，
并对「文本匹配失败」的片段做**顺序对齐兜底**（后端 sentenceList 与正文同序），不再静默退化成普通段落。

**③ 单词/句子失败：模型侧没有任何熔断 → 白等 2 分钟**
DB 里 `created_at → updated_at` 正好差 **2 分钟** = GLM 超时 60s + DeepSeek 超时 60s。
单词任务要输出全文每个词的释义，响应体最大 → 最容易超时；而
`CHUNK_FALLBACK_CHARS=5000` 对 1707 字的短文拆出来还是 1 批（`if (chunks.length===1) throw`）→ 等于没救。
修复（coze.js，全是新增）：
- **模型健康熔断**：`MODEL_HEALTH_FAIL_THRESHOLD`(2) 次失败 → `MODEL_HEALTH_COOLDOWN_MS`(300s) 冷却，
  冷却期内 `runWithModelFallback` **跳过该模型**（日志「模型熔断生效：跳过 GLM(主模型)（冷却中）」）；
  成功即归零；全部冷却时退回完整链路（避免永久不调用）。`getModelHealth()` / `resetModelHealth()` 导出，
  `/health.modelHealth` + `GET /api/model/reset-health` 可见。
- **超时细分重试**：`isTimeoutLikeError(err)` 判定超时类失败 → 按 `CHUNK_TIMEOUT_RETRY_CHARS`(1200) 重新拆批；
  **拆出来还是 1 批时再 `forceSplitIntoChunks(article, 2)` 按句边界强制劈半**（短文也能拆，且不打碎句子）。
- `__diag: { isTimeoutLikeError, splitArticleIntoChunks, forceSplitIntoChunks, getModelHealth, resetModelHealth }`
  只读暴露，**仅供 test_model_fallback.js 回归**，业务代码勿依赖。
